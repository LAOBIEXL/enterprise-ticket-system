# 企业内部工单系统 V1.0 需求与概要设计基线

- 文档状态：已确认内部开发基线，尚待客户正式评审
- 文档版本：1.0
- 最后更新：2026-08-27
- 适用版本：系统 V1.0
- 文档性质：需求分析与概要设计，不是物理表结构或最终 API 文档

## 1. 客户背景

客户公司约有 500 名员工，分为行政、人事、财务、销售和技术等部门。

当前员工遇到电脑故障、软件安装、账号申请和网络问题时，主要通过微信群、电话或私聊联系技术人员，存在以下问题：

- 问题容易遗漏；
- 员工不知道当前由谁处理；
- 技术人员容易重复处理；
- 处理过程没有统一记录；
- 出现责任问题时无法追溯；
- 管理层缺少问题数量和处理效率数据。

客户希望建设企业内部工单管理系统。第一期优先跑通核心业务流程，附件、消息通知、超时提醒和高级统计后续迭代。

## 2. V1.0 业务目标

- 所有正式问题都能形成工单记录；
- 每个处理中工单都有明确负责人；
- 员工可以查看自己的工单和处理进度；
- 技术主管能够统一分派和转派；
- 技术人员只处理分配给自己的工单；
- 每次关键操作都可以追溯；
- 通过状态和并发控制避免重复处理；
- 管理员能够管理用户、部门、角色和权限。

## 3. 角色定义

### 3.1 普通员工 `EMPLOYEE`

- 创建工单；
- 查看自己提交的工单；
- 查看处理进度和操作记录；
- 确认解决结果；
- 不认可结果时退回重做。

### 3.2 技术人员 `TECHNICIAN`

- 查看分配给自己的工单；
- 开始处理；
- 添加处理记录；
- 提交解决结果。

### 3.3 技术主管 `SUPPORT_MANAGER`

- 查看全部工单；
- 分派待分派工单；
- 转派已经分派或正在处理的工单；
- 执行技术人员具备的处理操作。

### 3.4 系统管理员 `SYSTEM_ADMIN`

- 管理用户；
- 管理部门；
- 管理角色和权限；
- 管理基础系统配置。

系统管理员默认不等于技术主管。若系统管理员需要查看或处理业务工单，应额外授予相应业务角色或权限。

一个用户可以同时拥有多个角色。

## 4. V1.0 功能范围

### 4.1 员工功能

- 登录；
- 创建工单；
- 分页查询自己的工单；
- 查看工单详情、当前处理人和处理记录；
- 确认解决结果；
- 退回未解决的工单并填写原因。

### 4.2 技术人员功能

- 分页查询分配给自己的工单；
- 开始处理工单；
- 添加处理说明；
- 提交解决结果。

### 4.3 技术主管功能

- 分页查询全部工单；
- 按状态、分类、提交人和处理人筛选；
- 分派工单；
- 转派工单；
- 查看完整处理历史。

### 4.4 管理员功能

- 用户管理；
- 部门管理；
- 角色管理；
- 权限管理；
- 用户角色分配；
- 角色权限分配；
- 工单分类管理。

## 5. V1.0 非目标

- 附件上传；
- 消息通知；
- SLA 和超时提醒；
- 高级数据统计；
- 多租户；
- 复杂审批流；
- 工单撤回；
- 工单驳回；
- 工单关闭后重新打开；
- 工单物理删除；
- 企业单点登录和外部账号同步。

## 6. 工单状态定义

| 状态码 | 中文名称 | 业务含义 | 数据约束 |
| --- | --- | --- | --- |
| `PENDING` | 待分派 | 工单已经提交，但尚未指定处理人 | 当前处理人为空 |
| `ASSIGNED` | 已分派 | 已指定技术人员，但尚未开始处理 | 当前处理人不能为空 |
| `PROCESSING` | 处理中 | 技术人员正在处理 | 当前处理人不能为空 |
| `WAIT_CONFIRM` | 待确认 | 技术人员已提交解决结果，等待员工确认 | 必须存在解决记录 |
| `CLOSED` | 已关闭 | 员工确认问题已经解决 | 必须记录关闭时间 |

`CLOSED` 是 V1.0 终态，不能再修改工单状态。

## 7. 状态转换表

| 业务动作 | 原状态 | 新状态 | 执行者 | 前置条件 |
| --- | --- | --- | --- | --- |
| 创建 `CREATE` | 无 | `PENDING` | 员工 | 标题、分类和问题描述合法 |
| 分派 `ASSIGN` | `PENDING` | `ASSIGNED` | 技术主管 | 处理人存在、有效并具备技术人员角色 |
| 重新分派 `REASSIGN` | `ASSIGNED` | `ASSIGNED` | 技术主管 | 更换处理人并填写原因 |
| 处理中转派 `REASSIGN` | `PROCESSING` | `ASSIGNED` | 技术主管 | 更换处理人并填写原因，新处理人重新接手 |
| 开始处理 `START` | `ASSIGNED` | `PROCESSING` | 当前处理人 | 操作者必须是当前处理人 |
| 添加记录 `ADD_RECORD` | `PROCESSING` | `PROCESSING` | 当前处理人 | 处理内容不能为空 |
| 提交结果 `RESOLVE` | `PROCESSING` | `WAIT_CONFIRM` | 当前处理人 | 解决方案不能为空 |
| 确认结果 `CONFIRM` | `WAIT_CONFIRM` | `CLOSED` | 工单提交人 | 操作者必须是提交人 |
| 退回重做 `RETURN` | `WAIT_CONFIRM` | `PROCESSING` | 工单提交人 | 退回原因不能为空 |

主流程：

```text
CREATE
  ↓
PENDING
  ↓ ASSIGN
ASSIGNED
  ↓ START
PROCESSING
  ↓ RESOLVE
WAIT_CONFIRM
  ├── CONFIRM → CLOSED
  └── RETURN  → PROCESSING
```

转派流程：

```text
ASSIGNED / PROCESSING
        ↓ REASSIGN
ASSIGNED
```

转派后保留全部历史记录，由新处理人重新执行开始处理。

## 8. 状态转换通用规则

每个状态动作都必须依次执行：

```text
验证登录状态
→ 验证接口权限
→ 验证数据权限
→ 验证当前状态
→ 条件更新工单
→ 写入操作记录
→ 事务提交
```

业务规则：

- 没有出现在状态转换表中的转换全部非法；
- 技术人员只能操作分配给自己的工单；
- 员工只能确认或退回自己提交的工单；
- 技术主管可以分派和转派，但必须填写转派原因；
- 状态更新必须携带原状态或版本号作为并发条件；
- 并发冲突返回 HTTP 409；
- 状态更新与操作记录写入处于同一事务；
- 已关闭工单只允许查询；
- 工单及操作记录不允许物理删除；
- 操作记录采用追加写入，历史记录不可直接覆盖。

| 查看自己的工单 | 是 | 是 | 是 | 由业务角色决定 |
| 查看分配给自己的工单 | 否 | 是 | 是 | 由业务角色决定 |
| 查看全部工单 | 否 | 否 | 是 | 由业务角色决定 |
| 分派或转派 | 否 | 否 | 是 | 由业务角色决定 |

## 10. 概念实体

### 10.1 Department 部门

表示行政、人事、财务、销售和技术等组织部门。V1.0 采用平级部门，不设计复杂部门树。

### 10.2 User 用户

统一表示员工、技术人员、主管和管理员。用户属于一个部门，可以拥有多个角色。

### 10.3 Role 角色

表示权限集合。V1.0 预置普通员工、技术人员、技术主管和系统管理员四类角色。

### 10.4 Permission 权限

表示具体系统操作能力。角色与权限通过关联实体建立多对多关系。

### 10.5 TicketCategory 工单分类

V1.0 预置电脑故障、软件安装、账号申请、网络问题和其他问题等分类。

### 10.6 Ticket 工单

表示员工提交的问题，保存当前状态、提交人、提交时所属部门、当前处理人和并发版本等当前信息。

### 10.7 TicketRecord 工单记录

记录创建、分派、转派、处理、解决、确认和退回等全部操作。记录只允许追加。

## 11. 概念 ER 关系

```text
Department 1 ───── N User
    一个部门拥有多个用户，一个用户属于一个部门

User M ─────────── N Role
    通过 UserRole 建立关系

Role M ─────────── N Permission
    通过 RolePermission 建立关系

TicketCategory 1 ─ N Ticket
    一个分类包含多个工单

User 1 ─────────── N Ticket
    关系一：作为 requester 提交人

User 1 ─────────── N Ticket
    关系二：作为 assignee 当前处理人
    一个工单在同一时刻最多有一个当前处理人

Department 1 ───── N Ticket
    保存工单提交时的来源部门快照

Ticket 1 ───────── N TicketRecord
    一个工单拥有多条操作记录

User 1 ─────────── N TicketRecord
    作为 operator 操作人

User 0..1 ──────── N TicketRecord
    作为 targetUser，例如分派目标技术人员
```

关系总览：

```text
Department
    └── User
          ├── UserRole ── Role ── RolePermission ── Permission
          ├── 创建 Ticket
          ├── 处理 Ticket
          └── 操作 TicketRecord

TicketCategory
    └── Ticket
          └── TicketRecord
```

## 13. 统一错误语义

| 场景 | HTTP 状态 | 响应体业务码 |
| --- | ---: | ---: |
| 参数或请求体不合法 | 400 | 400 |
| 未登录或登录已过期 | 401 | 401 |
| 没有接口权限或数据权限 | 403 | 403 |
| 工单、用户或分类不存在 | 404 | 404 |
| 当前状态不允许操作或发生并发冲突 | 409 | 409 |
| 未处理的服务端异常 | 500 | 500 |

## 14. V1.0 核心验收标准

- 员工能够创建工单并获得唯一工单编号；
- 新工单初始状态为 `PENDING`；
- 技术主管可以将待分派工单分配给有效技术人员；
- 两个主管同时分派时只能有一个操作成功；
- 非当前处理人不能开始或处理工单；
- 技术人员能够记录处理过程并提交解决结果；
- 只有工单提交人能够确认或退回结果；
- 员工确认后工单进入 `CLOSED` 且不可再次修改；
- 每次关键业务操作都生成不可覆盖的操作记录；
- 普通员工不能查看其他员工的工单；
- 所有受保护接口都必须验证登录和权限；
- 错误场景的 HTTP 状态与响应体业务码一致。

## 15. 设计假设与待后续细化项

当前采用以下内部开发假设：

- 用户由系统管理员维护；
- V1.0 不接入企业 SSO 或外部组织架构；
- 技术人员不能自行领取工单，由技术主管统一分派；
- 工单同一时刻只有一个当前处理人；
- 员工退回后仍由原处理人继续处理，除非主管转派；
- 系统管理员不自动拥有业务工单查看权限；
- V1.0 不提供自动关闭或超时关闭。

详细设计已经形成以下评审稿：

- [V1.0 数据库设计](./V1_DATABASE_DESIGN.md)：九张表的字段、索引、外键、事务、并发及迁移策略；
- [V1.0 API 契约](./V1_API_CONTRACT.md)：认证、DTO、分页、权限、数据范围和错误语义。

进入编码前仍需评审并冻结：正式登录凭据模型、旧用户表兼容方案、工单编号规则、创建接口幂等要求和测试数据策略。
